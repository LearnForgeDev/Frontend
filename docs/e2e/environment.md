# Окружение и данные для Playwright

## Существующая основа

Использовать [playwright.config.ts](../../playwright.config.ts), [fixtures.ts](../../tests/e2e/fixtures.ts), [auth.utils.ts](../../tests/e2e/auth.utils.ts), [core.const.ts](../../tests/e2e/core.const.ts) и [текущий workflow](../../.github/workflows/test.yml). Второй тестовый раннер или параллельную систему фикстур не создавать.

Текущая конфигурация запускает Chromium с одним worker, поднимает production preview на `http://127.0.0.1:4173`, сохраняет trace и скриншоты при ошибках. Preview использует уже собранный `dist`; сам Playwright сборку не выполняет.

Существующий CI выполняет установку зависимостей, typecheck, ESLint, unit-тесты, production-сборку и проверку её размера/синтаксиса. Затем он устанавливает Chromium, запускает публичные тесты, получает закреплённый backend, поднимает API/PostgreSQL/MinIO, ждёт готовности и запускает остальные браузерные тесты. После прогона сохраняет отчёты и удаляет контейнеры с томами.

```bash
npm run test:e2e -- --grep @public
npm run test:e2e -- --grep-invert @public
```

Это существующие команды CI, а не требование запускать тяжёлый стек локально. Для этой задачи достаточно лёгкой проверки документации; полноценные прогоны выполнять на CI.

`@public` применяется только к тестам, которым не нужен backend. `@backend` уже используется частью проверок сессии, но остальные backend-тесты могут быть без тега: текущая команда выбирает всё, кроме `@public`.

## Реальные зависимости

| Зависимость | Текущая настройка | Что проверяет |
| --- | --- | --- |
| Backend-General | SHA закреплён в `.github/workflows/test.yml`, checkout в `.ci/backend` | Реальные REST-контракты и авторизация |
| API | `CI_BACKEND_URL=http://127.0.0.1:8080`; браузер идёт через proxy preview | Работу сессии, куки и запросов одного origin |
| PostgreSQL | [tests/backend/compose.yml](../../tests/backend/compose.yml) | Персистентность и изоляцию школ |
| MinIO | `http://127.0.0.1:9000` | Presign, загрузку и чтение реальных байтов |
| SignalR | Backend hubs `/chatHub`, `/directChatHub` | Доставку сообщений и историю |
| Jitsi | В текущем compose публичный URL `https://meet.invalid` | Только выдачу параметров комнаты; медиа недоступны |

Для checkout закрытого backend CI использует repository secret `CI_BACKEND_TOKEN`. Пароли и токены не копировать в документацию, отчёты или сохранённый `storageState` в git.

## Базовые пользователи и расширения фикстур

Имеющийся [seed](../../tests/backend/Seed/Program.cs) создаёт `ci-owner`, `ci-teacher`, `ci-student`, одну школу с ID из `core.const.ts` и общий чат `Общий чат CI`. `login(page, role)` авторизует через настоящий API и записывает полученную сессию в localStorage. Саму форму входа проверять отдельно, без этого helper.

| Набор | Подготовка для будущих тестов |
| --- | --- |
| Владелец, преподаватель, ученик школы A | Использовать существующий seed; сверять реальные роли `Owner`, `Teacher`, `Student` |
| Новый пользователь без школ | Регистрировать уникальный аккаунт через UI или API подготовки |
| Участник A и B | Добавить вторую реальную школу и разные роли, чтобы проверять переключение и кеш |
| Посторонний пользователь | Создать отдельный аккаунт без членства в A; для проверки изоляции использовать существующую школу B, а не только случайный UUID |
| Служебный пользователь | Добавить отдельную роль/права backend для `/developer`; в базовом seed такого аккаунта нет |
| Приглашения | Создавать действующие, истёкшие и исчерпанные токены через backend; для последнего использования нужен отдельный тест |
| Заявки | Подготавливать Pending, Approved, Rejected и этап создания школы; не зависеть от ручного решения администратора |
| Курсы | Добавить поддержку текущих контрактов курсов в тестовый backend, уроки с содержимым, группы и назначенных/неназначенных учеников |
| Расписание | Дата относительно фиксированных часов теста, занятия до/во время/после окна входа, пересечения и участники |
| Материалы | Маленькие TXT, PNG, PDF и файл неподдерживаемого просмотра; имена с кириллицей и пробелами, одинаковые имена у разных файлов |
| Полноценный звонок | Отдельный стенд Jitsi, два browser context, тестовые устройства и разрешения; это расширение текущего CI |

## Изоляция и проверки

1. Один `browser.newContext()` на пользователя; для параллельного общения использовать два независимых контекста. Не передавать JWT одного пользователя другому.
2. Имена сущностей включают уникальный ID теста. Сохранять выданные сервером идентификаторы, не выбирать «первый файл» или «последний урок».
3. Создание/изменение в проверяемом флоу выполнять через UI. API разрешён для подготовки, чтения результата и удаления созданных данных в `finally`/teardown.
4. После успешной серверной операции проверять данные через API и после `reload`, при необходимости — во втором контексте. Один toast не доказывает сохранение.
5. Если удаление/очистка недоступны по контракту, использовать изолированную школу или удаляемую БД тестового прогона. Тесты не должны зависеть от порядка выполнения.
6. Получать форму/кнопку через `getByRole`, `getByLabel`, `getByPlaceholder`; ограничивать локатор нужной карточкой, строкой или диалогом. Для Lexical допустим существующий `.editor-input`.
7. Ожидания ответа регистрировать до клика. Проверять конкретный метод и pathname. Для UI применять `expect` с повторной проверкой; не добавлять фиксированные `waitForTimeout`.
8. Часы браузера использовать для таймеров интерфейса. Истечение токена, срока приглашения и серверные окна доступа требуют соответствующих данных/часов backend: `page.clock` не меняет время сервера.
9. Для happy path не подменять API, MinIO или SignalR. Ошибки воспроизводить реальными правами/данными, offline или управляемым отказом тестового стенда. Точечная подмена ответа допускается только в отдельной явно обозначенной проверке интерфейса и не считается интеграционным e2e.
10. Использовать существующую автоматическую фикстуру production-ошибок. Она следит за `pageerror`, сбоями JS/CSS и ответами ресурсов от 400; `304` является нормальным ответом кеша.
